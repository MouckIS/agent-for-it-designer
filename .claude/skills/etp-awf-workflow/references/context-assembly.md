# 上下文装配与交接

目的：每个 Agent 只拿必要信息，避免「检索到不同版本文档」导致结论冲突，也避免上下文被无关代码淹没。

## 1. 读取白名单

| 阶段 | 必读 | 可读 | 禁止 |
| --- | --- | --- | --- |
| A0 | manifest、artifact-manifest、基线、portfolio、各阶段产物 | 仓库状态、git log、校验脚本 | 写业务结论 |
| A1 | US 标识/链接、`etp-requirement-fetch` Skill、基线、已有 `01-source/` | 用户补充材料 | 业务规范、代码、历史设计 |
| A2 | ART-10、ART-11、ART-01、业务规范/领域词典 | 图谱的业务能力列表、历史 US | 大范围读源码、A3 以后产物 |
| A3 | ART-20、ART-22、ART-01、图谱/仓库、运行时证据、ART-04 | 相关历史设计、模块规范 | 读 A4 产物（不存在） |
| A4 | ART-20/21/22、ART-30/31/32、框架封装、检查项 Skill | 现有实现代码、类似功能、历史 ADR | 重读全仓库 |
| A5 | 全部正式产物、ART-01、ART-04、检查项 Skill | 独立检索图谱与代码 | 把 A1–A4 结论当证据 |

## 2. 版本纪律

- 只读 manifest 中登记的版本；发现磁盘上有更新文件但 manifest 未登记，先报告并让 A0 处理。
- 不允许把 `history`、`revision-history` 里的旧版本当作当前输入。
- 上游标 `STALE` 时，下游不得继续生成最终结论。
- 原始需求快照（`01-source/`）只读；需要修正必须重新获取并生成新版本。

## 3. 上下文预算

| 阶段 | 建议预算 | 超限处理 |
| --- | --- | --- |
| A1 | US 全文 + ≤30 张图片/附件 + ≤10 个外部链接 | 分批解析，先正文后附件 |
| A2 | ART-10 全文 + ≤5 份规范 + ≤20 个能力节点 | 规范只取命中条款 |
| A3 | ART-20 全文 + 图谱摘要 + ≤40 次代码检索 | 按模块分批，先宽后窄 |
| A4 | ART-30 全文 + 相关文件片段 + skill 规则 | 代码只读涉及的方法与相邻封装 |
| A5 | 全部产物 + ≥10 次独立检索 | 独立检索预算不得被压缩 |

## 4. 派发 prompt 装配清单

- [ ] Agent 名称与阶段号
- [ ] 必读文件绝对路径（含 skill 与 reference）
- [ ] 输入产物路径与版本（`A2-001:v2`）
- [ ] 基线四项 + graph lag_policy
- [ ] 本阶段输出目录
- [ ] 适用的检查项清单（A3～A5）
- [ ] 批次依赖与冲突（如有）
- [ ] 本轮修订指令（如有）
- [ ] 硬约束（不改代码、不越界、证据要求）
- [ ] 返回格式（≤15 行摘要）

## 5. 子代理返回契约

只返回摘要，不回传全文：

```text
stage: A3
artifacts: impact-package.yaml(A3-001:v1), impact-analysis.md, evidence-manifest.yaml
counts: mandatory=4, potential=8, high_risk=10, evidence_gaps=2
blocked: IMPACT-007 缺少运行时证据
need_human: 确认退款事件消费者是否在本次范围
next: A0 校验 C03，随后进入 G2
```

A0 收到摘要后必须自行读文件复核，摘要不作为验收依据。

## 6. 常见反模式

- 把所有历史文档一股脑塞给 A2 → 引用过期规范。
- A1 顺手解释业务规则 → 越过获取边界，产生未经确认的"需求"。
- A3 只查图谱不查代码 → 图谱漂移未发现。
- A5 复用 A3 的检索结果 → 共同盲区。
- 把 Markdown 当唯一产物 → 无法机器校验覆盖与追溯。
- 子代理顺手改了别的阶段文件 → 版本与责任混乱。
