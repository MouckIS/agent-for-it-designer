# 设计评审标准

## 1. 独立性

评审质量取决于「不看结论也能发现问题」。最低要求：

- 重新检索至少：每个 mandatory 触点的调用方 1 次、契约类触点的消费方 1 次、租户路径 1 次、配置引用 1 次。
- 至少 10 次检索/读文件/图谱查询操作，记录检索词与范围。
- 报告中列出「A3 未识别的触点」（如有）与代码证据。
- 不把 A3 的 `EVIDENCE` 编号当作自己的证据。

## 2. 八层检查

### 第一层 需求覆盖

| 检查 | 失败条件 |
| --- | --- |
| 规则-设计映射 | 代码类规则在覆盖矩阵中 Missing，且未说明「不涉及代码」 |
| AC-测试映射 | 任一 AC 无测试建议 |
| 范围 | 设计包含 US 未要求的能力（扩大范围） |
| 推断 | 推断项被当作已确认需求使用 |

### 第二层 影响覆盖

| 检查 | 失败条件 |
| --- | --- |
| 调用方 | 独立检索到 mandatory 触点的直接调用方未出现在 A3 |
| 数据 | 存在未识别的表/字段读写路径 |
| 消息 | 存在未识别的生产/消费方 |
| Job | 存在受影响但未识别的定时任务 |
| 配置/权限 | 存在未识别的配置项或权限点依赖 |
| 租户 | 存在未识别的租户上下文路径 |

失败必须给 `file:line` 或 `graph:node`；仅凭命名猜测不算。

### 第三层 设计正确性

- 是否沿用现有分层与封装；有无重复实现。
- 事务边界是否在 Service 层，是否存在嵌套事务或长事务。
- 写操作是否幂等，幂等键是否可落库。
- 并发是否有竞态（先查后写、共享缓存、状态机并发）。
- 异常是否统一处理，是否有吞异常/丢失上下文。
- 复杂度是否与需求匹配；简单需求是否引入不必要抽象。

### 第四层 数据与契约

- DDL 是否可逆；大表是否评估锁与耗时。
- 回填是否可重入；失败是否可续跑。
- API 是否向后兼容（新增可选字段、错误码不改变语义）。
- MQ 旧消费者是否仍可解析；是否需要双发/版本化 topic。
- 缓存一致性：更新顺序、失效策略、并发重建。
- 迁移与回滚是否成对。

### 第五层 SaaS 与项目检查项

- 按 `.claude/skills/etp-project-checklist/SKILL.md` 与 `.claude/skills/etp-legacy-saas-analysis/references/saas-checklist.md` 复核 A4 的结论。
- 检查是否有漏项、虚假 `not_applicable`、未处理的 `fail`。
- 任一项「无法确认」且被标为不涉及，视为风险。

### 第六层 发布与回滚

- 发布顺序是否与数据迁移顺序一致。
- 新旧版本是否可同时运行。
- 灰度维度是否合理（租户/比例/白名单）。
- 应用回滚后数据是否仍可读。
- 是否存在不可逆操作且无备份方案。

### 第七层 合理性

- 文件变更数与需求规模是否匹配（默认阈值 25）。
- 新增文件是否超过 3 个且无复用理由。
- 是否包含与需求无关的重构、重命名、格式化改动。
- 是否引入新中间件/新框架能力而无必要性说明。

### 第八层 跨 US 一致性

- 本 US 的预期文件变更是否与 `portfolio.yaml` 中其他 US 冲突。
- 依赖的上游 US 产物版本是否与设计引用一致。
- 依赖或冲突未登记时，直接列为阻断项。

## 3. 问题分级

| 级别 | 判定 | 影响结论 |
| --- | --- | --- |
| blocking | 导致需求无法实现、数据/资金/权限风险、契约不兼容、覆盖缺失、跨 US 冲突未处理 | FAIL |
| condition | 不阻断但必须在 G3 前完成（补监控、补测试、补文档） | CONDITIONAL_PASS |
| suggestion | 优化建议 | 不影响结论 |

问题必须写：`id, category, description, references, evidence, recommendation, return_to, status, blocking, check`。

`category` 除原有分类外，新增 `checklist`（检查项漏执行/虚假不适用）与 `cross_us`（跨 US 冲突）。

`check` 填违反的 C 规则或本 Skill 层级编号（如 `L3-事务边界`）。

## 4. 回流映射

| 问题类型 | return_to |
| --- | --- |
| 后端范围判断错误、内容块归属错误、剔除无理由 | A1 |
| 需求理解错误、规则遗漏、范围不清 | A2 |
| 影响范围遗漏、证据错误、风险漏判、跨 US 冲突未登记 | A3 |
| 方案不合理、ADR 缺失、兼容/迁移/回滚缺失、范围过大、检查项未回应 | A4 |
| 仅评审自身规则或结论需要修正 | A5 |

同一轮存在多个目标时，取最早阶段作为本轮 `target_agent`，其余问题保留在 `revision-instructions` 中待后续轮次处理。

## 5. 修订指令

```yaml
revision:
  id: REV-001
  review_id: A5-001
  target_agent: A4
  round: 1
  issues:
    - review_id: REVIEW-001
      target_section: "7.1"
      instruction: 补充全额退款兼容策略，说明旧调用方行为保持方式
      required_evidence: ["RefundService.java:118"]
      expected_output: ["修改后的 7.1 章节", "新增 ADR 或更新 ADR-002"]
  invalidated_artifacts: [A4-001:v1, A5-001:v1]
  preserved_artifacts: [A2-001:v2, A3-001:v2]
```

指令必须可执行：指到章节、说明要什么证据、期望产出什么。禁止「请完善设计」这种无法验收的指令。

## 6. 结论判定

1. 有任一 `blocking=true` 且 `status=open` → `FAIL`。
2. 无 blocking，但有 `condition`（如证据缺口、待补监控）→ `CONDITIONAL_PASS`，写 `conditions[]`。
3. 其余 → `PASS`。

不允许：用 suggestion 掩盖 blocking；把「评审人偏好」写成 blocking；在存在 open blocking 时给 PASS。

## 7. 轮次与争议

- 第 1 轮 FAIL：生成修订指令，回流目标阶段。
- 第 2 轮 FAIL：允许一次针对性重跑，但只针对未关闭问题。
- 超过 2 轮仍 FAIL：停止自动循环，写 `05-review/DISPUTE.md`，列出双方观点、证据、无法达成一致的原因、建议裁决人。

## 8. 常见误判

| 误判 | 纠正 |
| --- | --- |
| 只对照 A3 清单，未独立检索 | 必须自己查调用方与消费者 |
| 把「没有注释」当设计缺陷 | 关注行为与边界，不评文风 |
| 把「没用到某设计模式」当问题 | 简单实现优先，过度设计才失败 |
| 需求未提但代码里有的行为 → 要求设计覆盖 | 那属于范围外，标 suggestion 或交 A2 |
| 证据缺口直接判 FAIL | 高风险缺口才阻断；低风险可作 condition |
| 检查项标了 not_applicable 就放过 | 必须核对理由是否成立 |
